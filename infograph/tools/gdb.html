Install GDB on Kali Linux

Method 1 — Kali APT (recommended)
terminal 
sudo apt update
sudo apt install gdb -y
gdb --version
Method 2 — Build from source (latest)
terminal 
wget https://ftp.gnu.org/gnu/gdb/gdb-14.2.tar.xz
tar -xf gdb-14.2.tar.xz && cd gdb-14.2
./configure --with-python --disable-werror
make -j$(nproc) && sudo make install

Replace gdb-14.2 with the latest release from the GDB website.

Method 3 — pwndbg (exploit-dev enhanced)
terminal 
git clone https://github.com/pwndbg/pwndbg
cd pwndbg && ./setup.sh
Method 4 — GEF (exploit-dev enhanced)
terminal 
bash -c "$(curl -fsSL https://gef.blah.cat/sh)"
Tip:gdbserver ships with the gdb package on Kali – you get remote debugging for free. Compile your own targets with gcc -g -O0 so GDB can map source lines and variables.

Your First Debug Session

terminal 
# Start GDB on your binary (quiet mode hides the banner)
gdb -q ./program

# ---- now inside the (gdb) prompt ----
(gdb) break main          # stop at the start of main
(gdb) run                 # launch the program
(gdb) next                # step one line (over calls)
(gdb) print buffer        # inspect a variable
(gdb) bt                  # show the call stack
(gdb) quit                # leave GDB

Classic Crash-Debugging Workflow (Copy-Paste)

terminal 
# 1) Compile the target WITH debug symbols and no optimization
gcc -g -O0 -o program program.c

# 2) Reproduce the crash and capture a full report in one command
gdb -q ./program -batch -ex run -ex 'bt full' -ex 'info registers' > crash_report.txt

# 3) Reproduce interactively: stop where it dies and inspect the stack
gdb -q ./program -ex 'run' -ex 'x/16wx $rsp' -ex 'bt'

Exploit Development Workflow (Copy-Paste)

terminal 
# 1) Compile a deliberately vulnerable lab binary (lab only!)
gcc -g -O0 -fno-stack-protector -z execstack -o vuln vuln.c

# 2) Generate a De Bruijn cyclic pattern (pwntools)
python3 -c "from pwn import *; print(cyclic(200).decode())"

# 3) Crash the binary under GDB and feed it the pattern as input
gdb -q ./vuln -ex 'run'
# then, after the crash:  info registers eip   and   x/wx $eip

# 4) Convert the crashed EIP value back to the exact overflow offset
python3 -c "from pwn import *; print(cyclic_find(0x6161616c))"
Warning:Never compile with protections off or run GDB memory-writes outside an isolated lab. GDB disables ASLR by default – final exploits must be re-tested with set disable-randomization off.

FAQ — GDB Debugger

Frequently Asked Questions

Quick answers to the most common questions about GDB on Kali Linux – debug symbols, sudo requirements, step vs next, ASLR, core dumps, attaching to processes, and exploit development.

What is GDB?
GDB, the GNU Debugger, is the standard debugger on Linux and ships with Kali Linux. It lets you pause a program mid-execution, inspect registers and memory, step through source or assembly, analyze crashes and core dumps, and even patch live process memory. It supports C, C++, Rust, Go, Fortran, assembly and more.
Why does GDB say "no debugging symbols found"?
The binary was compiled without debug symbols. Recompile with the -g flag, e.g. gcc -g -O0 -o program program.c. Without symbols, GDB can still disassemble and debug at the machine-instruction level, but source lines, variable names and breakpoints by name won't work.
How is GDB different from pwndbg and GEF?
pwndbg and GEF are plugins layered on top of GDB that add exploit-development niceties: colorized context, checksec, heap analysis and cyclic offset helpers. Under the hood they are still GDB – every command on this page works with or without them installed.
Does GDB need root (sudo)?
No – debugging your own programs works as a normal user. You only need sudo to attach to processes owned by other users, or when Linux's ptrace restrictions (kernel.yama.ptrace_scope) block attaching to unrelated processes.
What is the difference between step and next?
next (n) executes one source line and steps over function calls – the call runs to completion. step (s) also executes one line but steps into any called function, letting you debug it line by line. For assembly-level precision use stepi and nexti, which advance exactly one machine instruction.
How do I pass arguments to the debugged program?
Either start GDB with gdb --args ./program arg1 arg2 (everything after --args is passed to the program), or set arguments from inside the session with set args arg1 arg2 followed by run.
Why are addresses different when I run the program outside GDB?
GDB disables ASLR (address space layout randomization) by default so addresses stay constant between debugging runs – check with show disable-randomization. Outside GDB, ASLR randomizes the stack, heap and (on PIE binaries) the code base on every run. Test final exploits with set disable-randomization off.
How do I debug a program that crashes instantly?
Use one batch command: gdb -q ./program -batch -ex run -ex 'bt full' -ex 'info registers'. It reproduces the crash, prints the full call stack with local variables, and dumps the registers – an instant crash report without any interaction.
Can GDB attach to a running process?
Yes. Start with gdb -p PID (sudo required for other users' processes) or use attach PID inside a session. The process is frozen the moment GDB attaches – plan for that pause on production systems, and always detach rather than quit to keep the process alive.
What does the x command do in GDB?
x examines raw memory. The syntax is x/COUNT FORMAT SIZE ADDRESS: x/s prints a string, x/16wx prints 16 hex words, x/32bx prints 32 bytes, x/10i disassembles 10 instructions. It is the single most important command for exploit development and crash analysis.
Can GDB analyze core dumps?
Yes. Enable core files with ulimit -c unlimited first, then open them with gdb ./program core. The bt command immediately shows the exact call chain that crashed – full post-mortem debugging without re-running anything.
Is GDB useful for exploit development and CTFs?
Absolutely. GDB is the backbone of binary exploitation: crash a vulnerable binary under GDB with a cyclic pattern, read the overwritten EIP/RIP, calculate the exact overflow offset, inspect the stack for payload placement, verify mitigations with checksec (pwndbg/GEF), and test shellcode by writing it directly into process memory before delivery.
