✦ How This Tool Works

What problem does this actually solve?

Before reaching for a terminal, you often just want a quick "is this port even reachable" answer, plus a reminder of what a port is normally used for and whether it's the kind of thing that shouldn't be open to the internet at all. This tool gives that fast browser-based signal, a built-in port reference so you're not looking up "what is port 1433" separately, and ready-to-paste commands for the real scan when you need ground truth.

Why can't a website do a real port scan?

Browsers deliberately don't expose raw TCP or UDP sockets to JavaScript — only higher-level protocols like HTTP(S) and WebSocket. That's a security boundary, not a missing feature: letting arbitrary web pages open sockets to any host:port would turn every browser tab into a potential scanning and internal-network-probing tool. This page works within that boundary rather than pretending to bypass it.

So what does "Reachable" actually mean here?

It means the browser's HTTP(S) fetch or WebSocket handshake got far enough to receive a response (even an error response, or a protocol-mismatch rejection) rather than timing out or getting an immediate connection-refused. That's a reasonable proxy for "something is listening on this port," but it can't distinguish a real service from a service that just happens to also speak enough HTTP to bounce the request, and a "no response" result can mean closed, firewalled, or simply CORS-blocked — the tool reports these possibilities honestly rather than picking one.

Why offer both HTTP(S) fetch and WebSocket checks?

A plain fetch() only tells you much when the service on the other end speaks HTTP. A WebSocket handshake attempt against a non-HTTP TCP port (say, SSH on 22 or a Redis instance on 6379) will still usually complete the underlying TCP connection before the protocol upgrade fails — so it's often a better open/closed signal for non-web ports than fetch is, even though the WS layer itself will always reject.

What's the difference between the nmap variants?

The default -sT TCP connect scan completes a full handshake and needs no special privileges — the direct terminal equivalent of what this page attempts in-browser. The optional -sS SYN ("half-open") scan is faster and stealthier but requires root/administrator privileges and raw-socket access. Both should only be run against hosts you own or are explicitly authorized to test.

Is anything sent to a server?

No server belonging to this site is involved — every check is a direct browser connection attempt to the host:port you entered, and the port reference table is a static built-in dataset. The one exception is the opt-in "Detect My Public IP" button, which calls a third-party API (ipify.org). Your draft input and settings persist only in this browser's local storage.
