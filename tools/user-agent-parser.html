✦ How This Tool Works

What problem does this actually solve?

Server logs, analytics exports, and support tickets are full of raw User-Agent strings that are unreadable at a glance. This tool turns them into the browser, engine, OS, and device someone was actually using, flags bots and automation tools so you can separate them from real visitors, and audits whole log dumps at once.

Why does my Chrome UA look so generic now?

Chrome has been progressively "freezing" and reducing the information in its User-Agent string (UA reduction) to limit passive fingerprinting, replacing the detail it used to carry with opt-in Sec-CH-UA Client Hints headers instead. A generic-looking Windows or Android UA on a recent Chrome version is expected, not a parsing failure.

Why does my iPad show up as a Mac?

Since iPadOS 13, Safari on iPad requests desktop sites by default and its User-Agent is deliberately identical to macOS Safari's — there's no "iPad" token to detect. Distinguishing an iPad from a real Mac reliably requires touch-capability detection or Client Hints, not the UA string alone.

Can a User-Agent string be trusted or used for security?

No — it's simply a value the client chooses to send and can set to anything. It's useful for analytics, layout decisions, and casual bot filtering, but treating it as an access-control or identity signal is unsafe; a request claiming to be "Googlebot" proves nothing on its own without verifying the source IP against Google's published ranges.

What are Sec-CH-UA Client Hints?

They're a newer, opt-in set of request headers (Sec-CH-UA, Sec-CH-UA-Platform, Sec-CH-UA-Mobile, and more) that a server explicitly requests, giving structured brand, platform, and mobile-flag data instead of parsing a single free-text string. They're the intended long-term replacement for detailed UA sniffing.

How reliable is the bot detection here?

It matches the UA string against a curated list of well-known crawler and HTTP-library signatures, which catches identifiable, honestly-labeled bots quickly. It can't catch a bot deliberately spoofing a browser UA — for that, combine this with IP/ASN verification and behavioral signals.

What's a good rogue-traffic or QA workflow with this?

Paste your access log's User-Agent column into the batch input. Sort by the Bot column to separate crawler traffic from real users, or by Browser/OS to spot which combinations are actually hitting your site — useful both for analytics QA and for noticing unexpected automated traffic.

Is anything sent to a server?

No. Every parsing, comparison, and generation feature here — including "Detect My Browser's UA" — runs entirely in your browser using the string you paste or your own navigator.userAgent. Your draft and settings only persist in this browser's local storage.
