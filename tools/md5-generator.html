Text Input Handling

The same text produces a different MD5 in UTF-8 vs UTF-16LE for anything outside plain ASCII — pick UTF-16LE only if you're matching a specific legacy tool that hashes strings that way.

Salting & Keying

Prepending or appending a salt to plain MD5 is common for legacy systems but is not considered secure keying — for anything security-sensitive, use HMAC-MD5 (or better, HMAC-SHA256) instead of concatenated salting.

Hash Strengthening (Iterated Hashing)

Iterating MD5 thousands of times does not make it suitable for password storage. This exists for compatibility with legacy systems that expect a specific double- or triple-hashed value — for real password hashing use bcrypt, scrypt, or Argon2.

✦ How This Tool Works

What problem does this actually solve?

Confirming a downloaded file matches what the publisher intended, signing a payload for a legacy API, or generating consistent lookup keys for a batch of values all come up constantly in day-to-day dev and ops work. This tool covers all three from one page, computed locally so nothing you hash — including file contents — ever leaves your browser.

Is MD5 still safe to use?

MD5 is cryptographically broken for collision resistance — a motivated attacker can craft two different files with the same MD5 hash, so it should never be relied on to detect deliberate tampering in a security-sensitive context. It remains perfectly fine, and still widely used, for accidental-corruption checks like verifying a download completed cleanly, content-addressable caching, or deduplication, where nobody is actively trying to fool the hash.

Why does the same text sometimes hash differently elsewhere?

Two things commonly cause this: text encoding and line endings. MD5 hashes bytes, not characters, so the same string hashes differently depending on whether it was encoded as UTF-8 or UTF-16 before hashing. A text file saved on Windows (CRLF line endings) will also hash differently from the same content saved on Linux or macOS (LF only) unless the line endings are normalized first — both are configurable in the settings above.

How is a file hashed without uploading it?

The File Checksum Verifier reads the selected file directly from disk into the browser using the File API, feeds it through the MD5 implementation in fixed-size chunks so even a multi-gigabyte file doesn't have to sit in memory all at once, and discards the bytes as it goes. The file's contents never touch the network — the whole computation happens locally.

What is HMAC-MD5 and how is it different from a salted hash?

Concatenating a salt to a message before hashing (md5(salt + message)) is vulnerable to length-extension-style attacks and isn't treated as secure keying by cryptographers. HMAC wraps the hash function in a construction specifically designed to resist that class of attack, which is why legacy systems that need a keyed signature use HMAC-MD5 rather than plain salted MD5.

Why offer iterated hashing if it isn't secure for passwords?

Some older forums, CMSes, and internal tools store values as md5(md5(password)) or similar for historical reasons, and matching that exact scheme is sometimes necessary for migration or compatibility work — not because it's a good way to protect a new system. The strong warning in the settings is there because the moment new credentials need hashing, the right tool is bcrypt, scrypt, or Argon2, not iterated MD5.
