✦ How This Tool Works

What problem does this actually solve?

Base64 shows up constantly in real work: embedding a small image or font directly in CSS via a data URI to save an HTTP request, decoding the payload segment of a JWT to inspect its claims, reading Base64-encoded fields in API responses or config files (Kubernetes Secrets, AWS Lambda payloads), and preparing attachments for email transport, which historically only supports 7-bit text. This tool covers encoding, decoding, and the format quirks (URL-safe alphabet, missing padding, line wrapping) each of those cases involves.

Why is there a "URL-safe" alphabet at all?

Standard Base64 uses "+" and "/", both of which are meaningful characters inside a URL (space-encoding and path separator respectively) and would need percent-encoding to survive in a query string. URL-safe Base64 swaps those two characters for "-" and "_", which are safe in URLs as-is — this is the variant JWTs and most web tokens use.

Why do some Base64 strings have no "=" at the end?

Padding characters exist only to make the output length a multiple of 4, and a decoder can mathematically reconstruct the correct amount from the string's length alone. Many token formats (JWTs especially) strip padding to save a couple of bytes; this tool's "Auto-restore missing padding" option adds it back before decoding so unpadded input still works.

What is a data URI, and when should I use one?

A data URI embeds a file's content directly inside a URL using the pattern data:<mime-type>;base64,<data>, letting a browser render an image, font, or icon without a separate network request. It's a good fit for small, frequently-reused assets (icons, tiny logos) but a poor one for large images, since Base64 inflates file size by roughly a third and the browser can no longer cache it independently.

Why did my decode fail on input that looks fine?

The most common causes are copy-paste line breaks or trailing whitespace the source didn't intend, a URL-safe string being decoded with the standard alphabet (or vice versa), and missing padding on strict decoders that don't auto-correct it. This tool's Decode Tolerance settings handle all three automatically, which is usually enough to fix a "invalid character" error on otherwise-valid input.

Is Base64 encryption or a security measure?

No — Base64 is purely an encoding scheme for representing binary data as printable text, and anyone can decode it instantly with no key required. Seeing a Base64 string is not evidence something is protected; treat it exactly the same as plaintext for anything sensitive, and use real encryption if confidentiality actually matters.

Is anything uploaded to a server?

No. Encoding, decoding, file handling, and the image preview all happen entirely in your browser using standard JavaScript APIs (btoa/atob and FileReader). Nothing you type or drop onto the page, including uploaded files, ever leaves the page.
