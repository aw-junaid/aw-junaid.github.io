SHA-1 Generator & Verifier

Hash text, hex, or Base64 input — one line at a time or as a whole message — sign it with HMAC-SHA1, salt and iterate it for teaching demos, verify it against an expected checksum, or compute a Git-compatible blob hash. Hash whole files too, batch-export the results, and everything runs entirely in your browser.
SHA-1 is cryptographically broken for collision resistance (the 2017 SHAttered attack) and, salted or not, is not suitable for password storage — use bcrypt, scrypt, or Argon2 for that. This tool is for checksums, Git compatibility, HMAC signature testing, and learning how hashing works, not for protecting secrets.

✦ How This Tool Works

What is SHA-1 still actually good for?

Despite being broken for collision resistance since the 2017 SHAttered attack, SHA-1 remains extremely common in practice: Git still hashes every object with it, many legacy APIs sign requests with HMAC-SHA1, and countless checksum files and file-integrity workflows still publish SHA-1 sums. This tool targets those real, still-current use cases rather than pretending SHA-1 has been fully retired.

Why does the same text sometimes hash differently elsewhere?

Hashing is byte-exact — a trailing newline, a stray space, or Windows-style CRLF line endings instead of Unix LF will all change the digest even though the text "looks" identical. The CRLF-normalization and trailing-newline settings exist specifically to reproduce (or avoid) the common `echo` vs. `echo -n` / `printf` mismatch, and the Byte Preview tab shows you exactly what was hashed so you can debug a mismatch.

Why is salting/iteration here if it's "not suitable for passwords"?

They're included to demonstrate the concept — how a salt changes every hash even for identical input, and how repeated hashing looks — for coursework and interviews, not as a real password-storage recipe. Actual password hashing needs an algorithm designed to be slow and memory-hard (bcrypt, scrypt, Argon2); plain iterated SHA-1 is fast enough that attackers can brute-force it at billions of guesses per second on modern hardware.

How does "Git blob hash mode" work?

Git identifies every object in its database by the SHA-1 of a small header prepended to the content: the literal text blob, a space, the content's exact byte length, a NUL byte, then the content itself. Enabling this mode reproduces exactly what git hash-object would output for the same bytes, which is useful for verifying Git-internal tooling or understanding how commits are addressed.

Can this hash large files?

Yes, up to the size cap you set (500 MB by default) — the whole file is read into memory and hashed in one pass using the browser's native Web Crypto API when available, which is fast even for large files. Raise the cap if you need to hash something bigger, but very large files will use correspondingly more browser memory.

Is anything sent to a server?

No — every hash, HMAC signature, and file digest is computed entirely inside your browser using the Web Crypto API, with an automatic pure-JavaScript fallback if Web Crypto isn't available (for example, when this page is opened directly from a local file instead of over HTTPS). Nothing you type or upload here ever leaves your device.

Why does verification work regardless of the output encoding I picked?

The Verification tab parses your expected checksum as either hex or Base64 and compares the raw digest bytes directly, rather than comparing display strings — so pasting a hex checksum still matches correctly even if you've set the output format above to Base64, or vice versa.
