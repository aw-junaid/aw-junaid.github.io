✦ How This Tool Works

What problem does this actually solve?

Storing plaintext or plain-hashed passwords is unsafe — bcrypt was purpose-built for password storage, combining a per-password random salt with a tunable cost factor that can be dialed up as hardware gets faster. This tool lets you generate realistic bcrypt hashes for testing an auth system, verify a login attempt against a stored hash, and benchmark the cost factor against your own machine before choosing a production value.

How is this actually computed?

Using bcryptjs, a pure-JavaScript implementation of the same Blowfish-based bcrypt algorithm used by libraries like Node's bcrypt, Python's bcrypt, and PHP's password_hash(). It runs entirely in your browser tab.

Why can't I just compare two bcrypt hashes to check if the passwords match?

Every bcrypt hash embeds its own randomly generated salt, so hashing the same password twice produces two completely different-looking hashes on purpose. That's the point — it defeats rainbow tables. To check a password, you always re-derive a hash using the salt already embedded in the stored one and compare those, which is exactly what the Verify tab and Hash Verifier utility do.

What does the cost factor actually control?

The cost factor sets the number of key-setup rounds as 2^cost, so each increment roughly doubles the time to compute a single hash. A higher cost makes brute-forcing dramatically slower for an attacker, but also slows down every legitimate login — the Cost Factor Benchmark utility helps find a value that costs an attacker real time while staying comfortable for your users.

Why does bcrypt only look at the first 72 bytes of a password?

bcrypt's underlying Blowfish key schedule has a hard 72-byte input limit — anything beyond that is silently ignored, meaning two passwords sharing the same first 72 bytes hash identically even if the rest differs. This rarely matters for typical passwords, but long passphrases or multi-byte Unicode strings can hit the limit sooner than expected, which is what the 72-byte warning flags.

What's the difference between $2a$, $2b$, and $2y$?

These are all bcrypt, differing only in minor implementation-detail fixes to the reference algorithm over the years. $2b$ is the current recommended prefix; $2y$ is what PHP's own crypt() historically produced and some legacy PHP systems still expect; $2a$ is the older OpenBSD-era prefix. They're cross-compatible in practice for verification, but generating with the prefix your existing system expects avoids confusion.

Is anything sent to a server?

No. Hash generation, verification, batch hashing, and benchmarking all run locally in your browser via bcryptjs. Nothing you type, including the password field, ever leaves the page. If "Never persist password" is enabled, the password is also excluded from local draft autosave.
