✦ How This Tool Works

Why does it sometimes refuse to derive Eq, Hash, or Copy?

Deriving these on a struct that isn't actually eligible produces a compile error (or, worse, a misleading one buried in a trait bound elsewhere). f64/f32 have no total ordering (NaN != NaN), so they can't back Eq/Hash. String, Vec, Box, and HashMap own heap allocations, so they can't be Copy. With the safety checks on, the tool drops the derive automatically and explains why in Conversion Notes instead of handing you code that won't build.

What's the Box<T> boxing about?

A Rust struct's size must be known at compile time, so a struct can never directly contain a field of its own type — that's infinite size. This shows up in real JSON for tree-shaped data (a comment with nested replies of the same shape, a category with subcategories). When "Auto-box recursive fields" is on, the tool detects a field whose structural shape matches an ancestor in its own path and wraps it in Box<T>, which is a fixed-size pointer regardless of what it points to.

How does it decide between rename_all and per-field rename?

If every renamed key in a struct follows the same convention (e.g. all originally camelCase), a single #[serde(rename_all = "camelCase")] on the struct covers all of them. The moment one field breaks the pattern — a key that's already snake_case sitting next to camelCase ones — the tool falls back to individual #[serde(rename = "..")] attributes so every key still round-trips correctly.

Why serde_json::Value instead of guessing on mixed types?

When the same JSON key holds genuinely different types across siblings (a string sometimes, a number other times), Rust's static typing can't represent that as one field type without an enum. The default falls back to serde_json::Value and flags it; turning on "Generate #[serde(untagged)] enum" instead produces a typed enum that serde tries each variant against in order — better ergonomics, at the cost of losing field-level errors when none of the variants match.

Does it detect chrono dates and UUIDs automatically?

Yes, each independently toggleable. ISO 8601 strings become chrono::DateTime<Utc> or chrono::NaiveDate (with #[serde(with = "...")] wiring where needed); RFC 4122 strings become uuid::Uuid. Both require the matching crate feature flags, which show up automatically in the Cargo.toml tab.

What do the built-in presets change?

Serde API Client favors rename_all, Option, and chrono/uuid detection for resilience to schema drift. Strict/Validated adds deny_unknown_fields and keeps the Eq/Hash/Copy safety checks on. Config File turns off renaming, derives Default, and uses #[serde(default)] everywhere. Public Library adds #[non_exhaustive], doc comments, and a builder for the root struct.

Is anything uploaded to a server?

No. Files you upload are read locally in your browser and the conversion happens entirely client-side — nothing is sent anywhere. Your draft and settings only persist in this browser's local storage.
