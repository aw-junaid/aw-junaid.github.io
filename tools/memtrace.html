C Memory Execution Tracer

Paste C code and step through it byte by byte — real address-space layout, hex/ASCII stack & heap grids, endianness, pointer arrows, and a live buffer overflow that corrupts a neighboring variable in front of you.
Scope, honestly stated: this is a teaching simulator, not a real interpreter — it traces a well-defined subset of C (int/float/double/char/bool locals, fixed char[] buffers, arithmetic, if/else, while, for, function calls with a real call stack, malloc/free, pointers, strcpy/manual buffer writes, and printf) by walking the parsed structure and modeling byte-accurate memory for it. It does not compile or execute anything, so real compiler layout, stack canaries, ASLR, and padding/alignment specifics won't match a real binary exactly — addresses and byte order are simulated but internally consistent, which is exactly what makes the buffer-overflow demo visible and safe to run.

✦ Core Concepts, In Plain Terms
Stack frame

A block of stack memory reserved the instant a function is called, holding its parameters and local variables. It's destroyed the instant the function returns — nothing in it survives.

Heap allocation

Memory you explicitly request with malloc and explicitly give back with free. It outlives the function that created it — which is exactly why forgetting to free it causes a leak.

Pointer

A variable that stores an address instead of a value. Dereferencing it (*p) means "go to that address and read/write what's there" — this tool draws that as an arrow.

Endianness

The byte order a multi-byte value is stored in. Little-endian (most desktops/phones) stores the least-significant byte first; big-endian stores the most-significant byte first.

Memory leak

A heap block that's still reachable-looking but never freed. The program keeps running, but that memory is gone until the process exits — the tracer flags these at program end.

Buffer overflow

Writing more bytes into a fixed-size buffer than it can hold. The extra bytes don't vanish — they land in whatever memory sits right after the buffer, silently overwriting it.

✦ How This Tool Works

What's actually different from the previous version?

Instead of just listing variables, every stack frame and heap block now has a real backing Uint8Array. Assignments encode the value into bytes at the chosen endianness, so the hex/ASCII grid you see is the same bytes a real program would hold in memory — including what spills over during an overflow.

How does the buffer overflow demo work?

A fixed char buf[8] is declared right before another variable on the stack. When the traced code writes more than 8 bytes into buf — via strcpy or a manual loop — the tracer writes those extra bytes straight into the next variable's byte range and flags every corrupted cell in red, exactly where it would land in real memory.

Are the addresses and layout realistic?

They're simulated, not pulled from a real compiled binary — real programs add padding, alignment, and ASLR that this tool doesn't reproduce. But the relative layout (stack grows down, heap grows up, buffers sit next to whatever was declared after them) mirrors how real memory is actually organized, which is what makes the overflow visible.

Is anything uploaded to a server?

No. Your code is parsed and simulated entirely in your browser — nothing is sent anywhere.
