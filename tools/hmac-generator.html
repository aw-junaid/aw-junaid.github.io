✦ How This Tool Works

What problem does this actually solve?

Almost every webhook system (Stripe, GitHub, Shopify) and many API authentication schemes sign requests with HMAC so the receiver can confirm a payload came from who it claims and wasn't tampered with in transit. This tool computes those signatures for testing your own integration, verifies an inbound signature against a payload and secret, and helps debug the all-too-common case of "my signatures don't match" — usually an encoding or whitespace mismatch.

How is this actually computed?

Entirely with your browser's native SubtleCrypto.sign() Web Crypto API — the same cryptographic primitive Node.js, Python, and every serious language binding call under the hood. Nothing is simulated or approximated; the output is production-correct HMAC-SHA1/256/384/512.

Why do hex and Base64 give different-looking results for the same HMAC?

The raw HMAC output is just bytes — hex and Base64 are two different text encodings of those same bytes. GitHub webhook signatures use hex (prefixed sha256=), while AWS Signature Version 4 and many others use Base64. Both represent the identical underlying signature; pick whichever your integration expects.

Why did my signature not match the one from my server?

The overwhelmingly common cause is a byte-level mismatch in the message — a trailing newline, different JSON key ordering, or re-serialized whitespace that your server's HTTP library adds or strips before your code sees it. HMAC treats the message as raw bytes, not as "the same JSON," so any re-serialization at all changes the signature. Always sign the exact raw request body, not a re-parsed and re-stringified version of it.

Is HMAC-SHA1 actually insecure?

SHA-1 itself has known collision weaknesses that matter for digital signatures and certificates, but HMAC's construction is specifically designed to remain secure as a message authentication code even with a weakened underlying hash — no practical attack breaks HMAC-SHA1 as a MAC today. That said, SHA-256 or better is the standard recommendation for any new system, since there's no real-world reason to keep using SHA-1 when better options are free.

Why does the tool warn about "constant-time" comparison?

If a server compares a computed and provided signature character-by-character and returns early on the first mismatch, an attacker can sometimes measure tiny timing differences to guess the correct signature one byte at a time. A constant-time comparison always checks every byte regardless of where the first difference is, removing that timing signal — most production HMAC-verification libraries provide one for exactly this reason.

Is anything sent to a server?

No. Every computation — HMAC generation, verification, batch signing, comparison, and random key generation — runs entirely in your browser via the Web Crypto API. Nothing you type, including your secret key, ever leaves the page. If "Never persist key" is enabled, the key is also excluded from local draft autosave.
