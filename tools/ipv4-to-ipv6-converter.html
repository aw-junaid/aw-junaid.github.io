IPv4 to IPv6 Converter

Turn IPv4 addresses into every standard IPv6-embedding form — IPv4-mapped, IPv4-compatible (deprecated), NAT64 (RFC 6052, well-known or custom prefix), 6to4, Teredo, and ISATAP — and go the other way too: paste any IPv6 address and auto-detect which scheme produced it, then pull the original IPv4 back out. Compare every method side by side, batch-convert whole lists, and export CSV — entirely in your browser.

Conversion Method

RFC 6052 defines exact bit positions for each prefix length so a NAT64/DNS64 gateway can strip the IPv4 address back out losslessly. Bits 64–71 stay reserved (zero) for every length except /96.
6to4 embeds the full public IPv4 address as the two hex groups after the fixed 2002::/16 prefix, giving every 6to4 user their own routed /48. It's deprecated in favor of native IPv6 and 6to4 relays are increasingly rare.
Teredo tunnels IPv6 over UDP through IPv4 NAT. The client port and client IPv4 are stored bitwise-obfuscated (inverted) so that NAT devices doing address/port translation don't rewrite them by mistake.
ISATAP treats IPv4 as a virtual link layer inside a site, encoding it in the last 64 bits after a standard 64-bit IPv6 prefix — commonly used for intranet-only IPv6 tunneling over an existing IPv4-only network.

✦ How This Tool Works

What problem does this actually solve?

Dual-stack sockets, NAT64/DNS64 gateways, 6to4 and Teredo tunnel brokers, and ISATAP intranets all need to embed an IPv4 address inside an IPv6 address using a specific, spec-defined bit layout. Getting that layout wrong breaks connectivity silently. This tool builds each form correctly per its RFC, and can decode an existing address back to confirm what's really embedded in it.

Which method should I actually use?

IPv4-mapped (::ffff:a.b.c.d) is what your OS uses internally for dual-stack sockets — you'll see it in logs, not on the wire. NAT64 is the modern production mechanism for IPv6-only networks reaching the IPv4 internet. 6to4 and Teredo are legacy transition mechanisms, largely superseded by native IPv6 and NAT64, but still show up in older infrastructure and CTF/networking coursework. ISATAP is intranet-only, never routed on the public internet.

Why does NAT64 support multiple prefix lengths?

RFC 6052 lets an operator's NAT64 prefix be /32, /40, /48, /56, /64, or /96 so the embedded IPv4 address can share space with an existing IPv6 addressing plan. Every length reserves bits 64–71 as zero except /96, which is why 64:ff9b::/96, the well-known default, is the simplest and most common choice.

Why is the Teredo client IPv4 and port "obfuscated"?

Teredo addresses cross NAT devices that sometimes rewrite IPv4 addresses and UDP ports in packet headers during translation. Storing the client's real IPv4 and port bitwise-inverted inside the IPv6 address itself means that even if a NAT along the path rewrites the outer headers, the original values embedded in the address survive untouched.

Is embedding a real IPv4 address in IPv6 a privacy concern?

Yes — 6to4, Teredo, and IPv4-mapped addresses all expose the exact public IPv4 (and for Teredo, the exact port) of the originating host to anyone who sees the IPv6 address, which can reveal rough geolocation or ISP. NAT64 and ISATAP addresses are typically only meaningful inside an operator's or organization's own network, so this is less of a concern there.

Is anything sent to a server?

No, with one exception: the "Convert My Public IP" button is opt-in and calls a third-party API (ipify.org) to look up your public IPv4. Everything else — parsing, embedding, reverse-decoding, batch conversion — runs entirely in your browser. Your draft and settings only persist in this browser's local storage.

Can I verify a conversion is reversible?

Turn on "Verify round-trip extraction" in Output Formatting. After generating an address, the tool immediately re-decodes it using the same logic as the Reverse Decoder and confirms the extracted IPv4 matches the original input — catching any edge case (like an odd prefix length) before you rely on the result.
