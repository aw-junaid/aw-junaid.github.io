Single-Byte Brute-Force

Tries all 256 possible single-byte keys against the ciphertext below and scores each result by English letter frequency (chi-squared). Classic first move for short, single-byte-XOR-encoded strings in CTF challenges.

Key-Length Detector

Estimates the repeating-key length using normalized Hamming distance between blocks (the core of breaking repeating-key XOR, as in the classic Cryptopals challenge) — a strong signal before attempting full key recovery.

Crib Dragging (Known-Plaintext)

If you know or suspect a fragment of the plaintext (a "crib" — e.g. a common word, header, or filename), XOR it against the ciphertext at every possible offset to recover fragments of the key. This is the core weakness of reused or short XOR keys: any known plaintext instantly leaks key bytes at that position, and — because the key is often short and repeating — those bytes frequently reveal or confirm the whole key.
✦ How This Tool Works

What problem does this actually solve?

XOR is the building block behind a huge amount of "obfuscation," legacy protocol scrambling, and CTF crypto challenges — it's fast, symmetric, and trivially wrong to use as real security. This tool covers both sides: encrypting/decrypting when you already know the key and format, and the actual recovery workflow (brute-force, key-length detection, crib-dragging) used when you don't — the same techniques used to break real single-byte and repeating-key XOR in the wild.

Why is XOR symmetric?

Because A XOR B XOR B = A. XOR-ing plaintext with a key produces ciphertext; XOR-ing that ciphertext with the same key reverses it exactly, byte for byte. There's no separate "decrypt" algorithm — encryption and decryption are the identical operation, which is why this tool uses one shared engine for both directions.

Is XOR encryption actually secure?

Only in one specific case: a truly random key at least as long as the message, used exactly once (a one-time pad). The moment a key repeats — which is what "repeating-key XOR" always does — the cipher becomes breakable via frequency analysis and Hamming-distance key-length detection, exactly like the tools in this page. Treat XOR as obfuscation, not encryption, for anything that actually needs to stay secret.

How does the key-length detector work?

It splits the ciphertext into blocks of a candidate length, computes the average normalized Hamming distance (bit differences) between those blocks, and repeats across a range of candidate lengths. Repeating-key XOR ciphertext blocks at the true key length correlate more (lower normalized distance) than blocks at other lengths, because identical key bytes were XORed against similarly-distributed plaintext bytes.

What is crib-dragging?

If you can guess a short plaintext fragment ("the", a filename, a known header), XOR-ing that guess against the ciphertext at every offset reveals what the key bytes would have to be at that position for the guess to be correct. Correct guesses tend to reveal printable, sensible key fragments; wrong guesses produce garbage — so scanning every offset quickly surfaces real key material, especially when the key is short enough to repeat within the message.

Is anything sent to a server?

No. Every computation — encryption, decryption, brute-force, key-length detection, crib-dragging, and batch processing — runs entirely in your browser. Nothing you type, including keys and ciphertext, ever leaves the page.
