✦ How This Tool Works

What problem does this actually solve?

A downloaded installer, ISO, or archive is only trustworthy if its checksum matches what the publisher listed. This tool computes real SHA-512/384/256/1 digests for text or files, right in your browser, so you can confirm integrity, generate signatures for webhook testing, or fingerprint content — without installing anything or uploading a file anywhere.

Is SHA-512 safe for hashing passwords?

Not on its own. SHA-512 is deliberately fast, which is exactly the wrong property for password storage — it makes brute-forcing guesses cheap for an attacker. Dedicated password-hashing functions like bcrypt, scrypt, or Argon2 are intentionally slow and memory-hard, and include a random salt per password automatically. Use SHA-512 for integrity checking and signatures, not password storage.

Why does the same input sometimes produce a different hash elsewhere?

Usually a hidden difference in the exact bytes hashed: trailing whitespace or a newline character, a different text encoding, byte-order marks, or a salt/prefix the other tool applied that this one didn't (or vice versa). Toggle "Trim trailing whitespace" and double-check the input encoding setting if a hash doesn't match what you expected.

What's the difference between a plain hash and HMAC?

A plain hash only proves the data wasn't altered, if you already trust its source — anyone can compute a matching hash. HMAC combines the message with a secret key, so only someone who knows the key can produce a valid signature. That's why APIs and webhook providers (GitHub, Stripe, and similar) use HMAC to let you verify a request genuinely came from them.

Is iterative hashing the same as a real key-derivation function?

No — re-hashing a digest N times slows things down a little, but a real KDF like PBKDF2, bcrypt, or Argon2 adds a unique salt per input automatically, uses a construction specifically resistant to GPU/ASIC cracking, and has a formally tunable cost parameter. Treat the iteration setting here as a learning demo of the general "stretching" idea, not a production technique.

Why offer SHA-1, SHA-256, and SHA-384 alongside SHA-512?

Published checksums aren't always SHA-512 — older software often ships SHA-1 or SHA-256, and some Linux distributions use SHA-384. The Algorithm Comparison tab computes all four for the same input so you don't have to guess which algorithm a given checksum is before you can verify it.

Is anything sent to a server?

No. Every computation here — text hashing, file hashing, HMAC signing, and file comparison — runs entirely in your browser using the native Web Crypto API. Files you select are read locally and never uploaded. Your draft and settings only persist in this browser's local storage.

Why might hashing fail entirely?

The Web Crypto API's crypto.subtle is only available in a secure context (a page served over HTTPS, or localhost during development). If this page is somehow loaded over plain HTTP, hashing won't be available — reload it over HTTPS to fix that.
