Python Memory & Reference Tracer

Paste Python code and step through it — watch each scope hold names that point at real objects on the heap, watch reference counts rise and fall as names are added or removed, and catch a live shared-reference bug corrupt a list you never touched.
Scope, honestly stated: this is a teaching simulator, not CPython — it traces a well-defined subset of Python (int/float/str/bool/None locals, list/dict objects, arithmetic, if/elif/else, while, for x in range(...) and for x in list, function calls with a real call stack and closures over module scope, list methods like append/pop, and print()) by walking the parsed structure and modeling how CPython actually stores things: every value is an object on the heap, and every name in a scope is just a reference to one. ✦ Core Concepts, In Plain Terms
Scope / namespace

A dictionary-like mapping from names to objects. Calling a function pushes a new scope with its own names — it holds no data itself, just references to objects that live elsewhere, on the heap.

Object heap

Where every actual value lives — every int, string, list, dict. Unlike C, Python code never manually allocates or frees this memory; the interpreter creates objects as needed and reclaims them automatically.

Reference, not a copy

b = a does not copy a's value — it makes b point at the exact same object as a. For immutable types (int, str) this is invisible; for mutable types (list, dict) it means changes through either name are visible through both.

Reference counting

Every object tracks how many names/containers currently reference it. Each new reference increments the count; each one that goes away (reassigned, or its scope ends) decrements it. At zero, CPython frees the object immediately.

Garbage collection

What happens when an object's refcount hits zero (or a reference cycle is detected). Unlike C's free(), this is automatic — you never explicitly deallocate anything in ordinary Python code.

Aliasing bug

The Python-native "memory corruption": two names end up referencing the same mutable object without you intending it — often via b = a or a mutable default argument — so mutating one silently changes what the other sees.

✦ How This Tool Works

Why isn't there a "stack" like the C version?

Because Python doesn't have one in the C sense. A Python "scope" only ever holds name→object references — never actual data — so this tool models it honestly as a Scopes panel next to an Object Heap, instead of pretending Python has raw stack bytes it doesn't.

How does the aliasing-bug demo work?

When code does b = a for a list, both names are pointed at the exact same heap object — its refcount goes to 2. If the code then mutates through one name (e.g. a.append(...)), the tracer flags that the object reachable through b changed even though b was never assigned to, exactly like it would surprise you in real Python.

Are the object IDs real memory addresses?

No — they're simulated, generated the same way CPython's id() would look (an opaque hex value), so you can see "these two names share an id" without this tool needing to match a real interpreter's actual memory layout.

Is anything uploaded to a server?

No. Your code is parsed and simulated entirely in your browser — nothing is sent anywhere.
