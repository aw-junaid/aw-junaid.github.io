✦ How This Tool Works

What problem does this actually solve?

Checking header security by eye means cross-referencing a dozen header names against what you remember they should look like. This tool parses a raw response once, checks it against the current recommended security headers, flags information leaks, cookie misconfigurations, caching conflicts, and CORS mistakes, and rolls it all into a quick grade — the way a manual review would, but instantly.

Why paste headers instead of just entering a URL?

A page running in your browser can only read the response headers of a cross-origin request if the server explicitly exposes them via Access-Control-Expose-Headers — that's a deliberate browser restriction, not a bug in this tool. The Live Header Fetch utility below will try, and clearly shows when it's blocked, but pasting the output of curl -I or your DevTools Network tab is the reliable path to the complete header set.

What does the security grade actually measure?

It's a heuristic, not a certification: each enabled security header contributes to the score based on whether it's present and well-configured, disclosure headers subtract a little, and cookies missing Secure or HttpOnly subtract a little more. Treat it as a fast way to spot gaps, then use the Security tab for the specific reasoning behind each finding.

Why are Server and X-Powered-By flagged?

Neither header is a vulnerability by itself — but a version string like Server: nginx/1.18.0 tells an attacker exactly which known CVEs to try first, and X-Powered-By: Express narrows down the entire attack surface to one framework's quirks. Removing or genericizing them is a low-cost way to slow down reconnaissance.

What's wrong with wildcard CORS plus credentials?

The CORS spec explicitly forbids combining Access-Control-Allow-Origin: * with Access-Control-Allow-Credentials: true, because it would let any site on the internet read authenticated responses on a user's behalf. Browsers reject the combination outright, so seeing it usually points to a server reflecting the request's Origin header without validating it — worth double-checking.

Why does SameSite matter for cookies?

SameSite controls whether a cookie is sent on cross-site requests. Without it, browsers apply their own default (currently Lax), which can silently change cookie behavior across environments. SameSite=None is meant for cookies that genuinely need to be sent cross-site (e.g. embedded widgets), but browsers require it to be paired with Secure — without that pairing, the cookie is rejected entirely.
