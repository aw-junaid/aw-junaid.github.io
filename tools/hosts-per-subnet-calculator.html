✦ How This Tool Works

What problem does this actually solve?

Sizing a subnet by hand means finding the smallest power-of-two block that fits a host count, then repeating that for every VLAN in a design while making sure none of the resulting blocks overlap and the whole plan still fits inside the address space you were given. This tool does the sizing, the ordering, and the non-overlapping allocation in one pass, and re-does it instantly every time a requirement changes.

Why does it ask for a growth buffer instead of just the current host count?

A subnet sized exactly to today's device count is full the moment the team hires or a few IoT devices get added, and re-subnetting later usually means renumbering. Applying a buffer percentage up front (a common real-world default is 20–50%) rounds sizing up to the next power-of-two block that has real headroom, without you having to guess a padded number by hand each time.

Why do cloud subnets need more reserved addresses?

On a traditional LAN only the network and broadcast address are unusable. AWS reserves five addresses in every VPC subnet (network, the VPC router, two for DNS, and one held for future use, plus broadcast), Azure reserves five for similar reasons, and Google Cloud reserves four. A /28 that comfortably fits 14 hosts on-prem only fits 11 in an AWS subnet — the Cloud & Reserved-IP Overhead setting builds that difference into the sizing.

How does the VLSM allocation avoid overlapping subnets?

Requests are sorted largest-first by default (classic VLSM practice) and packed sequentially from the start of the base network, with each subnet's starting address rounded up to the next boundary its block size requires. That alignment is what guarantees every resulting subnet is a valid, non-overlapping CIDR block rather than an arbitrary address range.

What happens if the base network is too small?

Once a requested subnet no longer fits in the remaining space, it's marked as unallocated in the Allocation Table rather than silently wrapping into addresses already in use. With "Stop allocating on overflow" enabled, everything after the first failure is left unallocated too, so it's obvious the base network (or a /prefix in the requests) needs to grow.

What's the DHCP pool range for, exactly?

Most subnets hold a handful of statically-assigned addresses — the gateway, a couple of switches, a printer — before the rest of the usable range is handed to a DHCP scope. Setting a static-reserved count carves that many addresses off the front of each subnet's usable range and reports the remainder as the actual DHCP pool you'd configure.
